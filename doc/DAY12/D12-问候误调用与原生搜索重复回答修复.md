# 问候误调用与原生搜索重复回答修复

## 实际原因

- 用户反馈的 `hello` Run 属于新会话，context.messageCount 为 1，排除旧会话任务干扰。模型自行将问候扩展为列文件，先调用 list_files，再 finish_research；原提示词只说普通交流可以直接回答，对纯问候禁止扩大任务的约束不明确。
- React 官网问题的持久事件包含一次 search_web、一个 994 字的 text:0 阶段正文，以及后续最终回答。观测显示收集阶段只有 research:1，finishReason 为 stop，说明供应商原生搜索及其后续正文发生在同一个模型步骤内。
- prepareStep 只在下一个步骤开始时切换收集职责，无法阻止供应商在本步搜索后继续回答。执行器又把工具后的所有自由正文发布为阶段消息，随后独立最终生成，形成用户看到的重复答案。这不是前端把最终消息重复追加。

## 修复

- 基础指令明确：纯问候、寒暄、致谢和确认收到不调用文件、检索、联网或交接工具；有资料或联网开关开启都不是调用理由。包含问候的实际任务仍按具体请求执行，不做问候关键词短路或固定回复。
- list_files 的描述明确限定为用户的文件清单/数量请求，或具体资料任务需要确认文件身份。
- 初始步骤就说明原生搜索可能同一步返回，并要求工具后保持收集职责，不展开完整最终答案。
- 执行器依据真实 start-step 和 search_web tool-call 识别原生搜索同一步的后续正文。该正文仅进入已有的待核验草稿，不发布为阶段消息；最终回答仍依据真实搜索证据生成和验证来源。
- 下一模型步骤重置该标记，本地工具 briefing 和下一步真实进展保持原流式路径。不按答案长度、相似文本或问题关键词裁剪，不影响最终答案正文，不修改用户历史数据。

## 实际验证

- 类型检查和三个修改文件的定向 ESLint 通过。
- 通过现有本地 API 与 Workflow 执行六组真实回归：两次独立 hello、联网开启时的你好、带问候的列文件请求、列文件历史后的 hello、同会话中的 React 官网搜索请求。
- 四个纯问候场景工具调用均为 0；混合列文件请求仍调用 list_files 和 finish_research，未被问候规则误拦截。
- React 官网场景调用 search_web，最终回答 979 字、3 条真实网页来源，持久阶段正文字符数为 0；每轮仅保存一条最终助手消息。该结果验证本次执行及持久事件，不宣称所有生成内容已经完成质量评测。
- 本次自行创建的验收会话通过现有接口软删除，临时诊断和回归脚本已删除；用户反馈的原始会话保留。

## 边界

工具选择仍由模型按明确指令判断，本次未引入额外意图分类模型、关键词问候拦截或新框架。原生搜索续写的重复展示由执行器按事件边界处理；这不保证供应商不会生成额外正文或产生对应 Token 费用。历史里已经保存的旧阶段正文不回写、不隐藏。
