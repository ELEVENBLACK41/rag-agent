# DAY8 后续高质量检索升级规划

状态：规划中，暂不实施。

## 目的

DAY8 建立“中文关键词 + 向量 + RRF + rerank”的可追溯基线。项目功能冻结并完成
DAY16 评测后，再用同一批固定资料、问题和评分规则，对参数或算法升级做前后对比。
任何升级都必须能说明收益、成本和退化案例，不能只因主观回答更像“高质量”就替换基线。

## 当前基线配置

| 项目 | DAY8 基线 |
| --- | --- |
| Embedding | `alibaba/qwen3-embedding-0.6b`，1024 维 |
| 关键词 | 中文完整短语 + 相邻双字词；拉丁词、数字、版本号直接匹配 |
| 关键词 TopK | 12 |
| 向量 TopK | 12 |
| 融合 | RRF，`rankConstant = 60` |
| rerank 候选数 | 12 |
| rerank | `voyage/rerank-2.5-lite`，超时 8 秒、无重试 |
| 最终 TopK | 6 |
| 失败降级 | 向量失败保留关键词；rerank 失败保留 RRF 前列 |

这些参数全部集中在 `lib/retrieval/config.ts`，每个 Run 的 `retrieval_trace` 会保存使用
的配置、候选 Chunk ID、融合顺序、rerank 前后顺序和降级原因。

## 升级实验顺序

1. 先只调整一个参数：`keywordTopK`、`vectorTopK`、RRF 常数、rerank 候选数或最终 TopK。
2. 在开发集观察排序与失败案例；开发集可用于筛掉明显无效的方案，但不能产出发布结论。
3. 只将候选方案在冻结的留出集运行一次，并与 DAY8 基线对照。
4. 若收益覆盖成本和退化风险，记录版本、变更原因、结果后再替换默认值；否则保留基线。
5. 只有基线已无法满足明确评测目标时，才讨论新增中文分词、混合索引、模型或数据库能力；届时先说明依赖成本和替代方案，征得确认后实施。

## 必须对比的指标

| 维度 | 指标 | 口径 |
| --- | --- | --- |
| 检索 | 文档级 Precision@5、Recall@10 | 与块级分开计算；相关证据必须人工标注。 |
| 检索 | 块级 Precision@5、Recall@10、nDCG@10 | 记录等价证据集合和相关性等级。 |
| rerank | 开关前后 nDCG@10、候选顺序变化 | 不预设 rerank 必然提升。 |
| 回答 | 引用支持准确率、无依据结论率、Task Success | 引用与回答正确性分别人工审查。 |
| 效率 | p50/p95 延迟、排队时间、rerank 耗时 | 明确是否包含冷启动和重试。 |
| 成本 | 输入 Token、rerank 输入量、模型费用估算 | 与平台账单分开记录。 |
| 稳定性 | 降级率、首个失败阶段、恢复结果 | 区分向量失败、rerank 超时、配额失败。 |

没有完整相关证据标注时，日志只能显示候选数量、命中情况和人工样例，不能宣称
Recall@K；无标注线上任务应显示“未评测”。

## 报告模板

每次实验写入独立 Markdown 和 JSON 结果，至少包含：

- 数据集版本、资料快照、样本量、开发集或留出集标记、人工评分人和日期。
- 基线与候选的完整参数表、模型/解析器/索引版本。
- 每项指标的分子、分母、结果和置信限制，不只写百分比。
- 典型提升、无变化和退化案例，以及首个失败阶段与根因。
- 延迟、Token、费用与降级率变化。
- 采用或拒绝升级的结论；若采用，必须附回归样例与可回退的旧参数。

## 当前不做

- 不提前替换 DAY8 默认参数，不新建分词服务、向量数据库或第二套检索框架。
- 不用模型自动评审代替人工标准答案；模型评审只能作为抽检建议。
- 不把访客私人正文或 Trace 自动加入长期评测集。
- 不根据单题效果、演示回答或未标注日志宣称召回率提升。
