# 单知识库访客隔离与 30 分钟失效方案

状态：待实施

## 1. 目标

生产首版只向用户展示一个“知识库”，不提供多知识库创建或切换功能。

- Admin 上传的案例文件永久保存，并对所有访客可查询。
- Visitor 上传的文件只对当前 Visitor 可见。
- Visitor 的临时资料在最后一次写操作 30 分钟后失效。
- 失效后，Visitor 的文件、图片附件、会话、Run 和结构审计全部隐藏。
- Admin 可以持续查看所有 Visitor 数据，包括已经失效的数据。
- 本阶段只完成身份、数据归属和访问隔离，不处理恶意文件、限流和物理清理。

> “失效”表示 Visitor 无法继续访问，数据不会物理删除。页面不能向用户描述为“30 分钟后彻底删除”。

## 2. 用户看到的单知识库

页面仍只有一个知识库入口，服务端按身份合并可见内容。

| 身份 | 文件列表与检索范围 |
|---|---|
| Visitor A | Admin 永久案例文件 + Visitor A 未失效文件 |
| Visitor B | Admin 永久案例文件 + Visitor B 未失效文件 |
| Admin | Admin 永久案例文件 + 所有 Visitor 文件，包括已失效数据 |

Visitor A 永远不能读取 Visitor B 的文件、会话、图片、审计和 Run。内部数据分区不暴露为多个知识库，因此不增加用户操作成本。

## 3. 内部数据归属

继续使用 `workspaceId` 作为隔离边界：

- 固定一个 `owner` Workspace，保存 Admin 上传的永久案例资料。
- 每个匿名 Visitor 创建一个独立的 `visitor` Workspace。
- Visitor Cookie 只标识 Visitor，实际 `workspaceId` 必须由服务端查询得到。
- 禁止接受客户端提交的 `workspaceId` 作为授权依据。

`workspaces` 增加：

```ts
mode: "owner" | "visitor";
expiresAt: Date | null;
```

Admin Workspace 的 `expiresAt` 为 `null`。Visitor Workspace 的 `expiresAt` 为最后一次写操作时间加 30 分钟。

## 4. Visitor 身份

Visitor 第一次访问时，服务端执行：

1. 生成高熵随机 `principalId`。
2. 创建对应的 Visitor Workspace。
3. 创建 Principal 与 Workspace 的关联。
4. 写入签名的 `HttpOnly` Cookie。

Cookie 使用 `Secure`、`SameSite=Lax` 和合理的域名范围。所有 API 通过统一的 `resolveRequestIdentity()` 获取当前身份和 Workspace。

本地模式继续解析为现有本地 Workspace；Admin 继续使用现有 GitHub Owner 登录。

## 5. 30 分钟失效规则

以下写操作会把当前 Visitor Workspace 的 `expiresAt` 更新为“当前时间 + 30 分钟”：

- 上传或重新上传文件；
- 创建新会话；
- 提交新问题或重试 Run。

刷新页面、读取文件和查看历史不会续期，避免只保持页面打开就永久占用空间。

每个 Visitor API 请求都实时检查 `expiresAt`。到期后：

- 文件和图片附件列表只保留 Admin 案例资料；
- Visitor 会话列表返回空；
- 原会话、Run、来源和附件接口返回 404；
- Visitor 结构审计不再返回旧报告；
- 正在显示的页面在下一次请求时清空临时状态；
- 再次写入时创建新的 Visitor Workspace，不恢复旧空间。

失效判断不依赖 Cron，保证达到时间后立即阻止 Visitor 访问。

## 6. 查询与权限规则

所有读取、删除和状态接口必须校验当前 Workspace，不能只根据资源 ID 查询。范围包括：

- `batchId`、`importId` 和导入进度；
- `conversationId`、`runId` 和 Run Event；
- `snapshotId`、`chunkId` 和引用来源；
- `fileVersionId`、图片附件和派生视觉文件；
- 结构审计报告。

无权访问和已经失效的数据统一返回 404，避免暴露资源是否存在。

Admin API 在通过 Owner 鉴权后可以忽略 Visitor 的 `expiresAt`，普通 Visitor API 不能提供绕过参数。

## 7. 公共案例与 Visitor 资料联合检索

一次 Visitor 回答需要同时查询：

1. Admin 案例 Workspace 的当前发布快照；
2. 当前 Visitor Workspace 的未失效快照。

为了让历史回答固定资料版本，Run 需要同时记录公共快照和 Visitor 快照。首版可以保留现有 `snapshotId` 作为 Visitor 快照，并增加可为空的 `publicSnapshotId`。

检索、引用读取和来源预览只能访问该 Run 固定的两个快照，不能临时读取其他 Visitor 的最新数据。

## 8. Admin 查看方式

Admin 管理页增加 Visitor 数据入口，展示：

- Visitor Workspace 标识；
- 创建时间、过期时间和当前状态；
- 文件、图片附件、会话、Run 和结构审计；
- 数据属于哪个 Visitor Workspace。

Admin 上传仍写入 Owner Workspace，并作为永久案例资料向所有 Visitor 开放。Visitor 上传不得写入 Owner Workspace。

## 9. 实施顺序

1. 为 Workspace 增加类型和过期时间。
2. 实现签名 Visitor Cookie 与统一身份解析。
3. 将上传、会话、Run、检索、来源、附件和审计改为显式接收 `workspaceId`。
4. 增加 Owner 案例快照与 Visitor 快照的联合检索。
5. 增加请求时过期检查和前端失效后的状态清理。
6. 增加 Admin 的 Visitor 数据只读查看入口。
7. 完成双浏览器隔离与过期验收后，再开放 Production 门禁。

## 10. 首版验收

- 两个无痕窗口分别获得不同 Visitor Workspace。
- A 上传的文件、图片、会话和审计不会出现在 B 中。
- A、B 都能查询 Admin 上传的永久案例资料。
- A 不能通过复制 ID 或 URL 读取、删除 B 的资源。
- 最后一次写操作 30 分钟后，A 的临时文件、图片、会话和审计全部消失。
- A 过期后不能继续读取旧 Run 的事件和来源。
- Admin 仍能查看 A 的全部过期数据。
- Admin 上传的案例资料不会过期，也不会被 Visitor 删除。
- Run 固定公共和 Visitor 两个快照，刷新后引用范围不变化。

## 11. 当前不做

- 恶意文件检测与内容审核；
- IP、Visitor 或全站限流；
- CAPTCHA；
- 过期数据物理删除；
- Visitor 登录、跨设备找回和多知识库管理；
- PostgreSQL RLS 第二层隔离。

上述能力不影响本方案的基础身份隔离，但正式扩大流量前需要继续补齐容量、费用和滥用控制。
