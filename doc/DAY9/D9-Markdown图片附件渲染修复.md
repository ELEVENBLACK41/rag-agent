# Markdown 图片附件渲染修复

用户反馈：Markdown 使用 `![[Pasted image 20251017153449.png]]` 嵌入图片，图片已上传为附件，但原文预览没有显示。

## 原因与修复

- 已有 Obsidian 转换与同快照附件解析能力，但 Streamdown 2.6.0 的默认 harden 在 `urlTransform` 之前执行，裸相对图片文件名被直接替换为 blocked 提示。实际渲染探针复现了此行为。
- 图片 URL 中的空格、中文会被 Markdown 编码；原来的查询参数包装未还原路径，可能把 `%20` 等编码文本当成文件名进行匹配。
- 新增局部图片插件，在 HTML 清洗后、harden 前将本地图片转为当前 Run/Chunk 的附件接口地址。图片路径仅解码一次再作为查询参数编码；后续仍经过 harden 与地址检查。
- 保留默认 HTML 安全清洗，显式保留原有 mark 标签的颜色数据属性；远程、data 和绝对地址不直接加载。
- 服务端附件读取、快照权限、同目录/根目录/唯一短名匹配逻辑保持原有行为，无新增依赖或数据库变更。

## 实际验证与边界

- 使用已安装的真实 Streamdown 和 React 服务端渲染，验证 Obsidian 原始语法、中文目录和文件名、空格编码、引用式图片均产生正确附件路径。
- 验证远程、data、绝对路径不会产生图片请求，围栏代码不会被转成图片；原有 mark 颜色数据保留，危险事件属性被移除。
- 定向 ESLint、沙箱外完整 TypeScript 检查通过。沙箱内 TypeScript 因既有 class-variance-authority 链接访问限制失败，未重装依赖。
- 本轮未导入用户文件、调用模型或完成用户实际文件的浏览器端到端验收；渲染验证不等于该图片已存在于对应 Run 的快照。
- 图片若在旧回答生成之后补传，旧 Run 仍使用原快照，需要新建一轮回答再打开来源。PNG/JPEG 可作为附件展示，不代表模型已分析独立图片内容。

参考：[Streamdown 安全过滤与 URL 转换](https://streamdown.ai/docs/security)。
