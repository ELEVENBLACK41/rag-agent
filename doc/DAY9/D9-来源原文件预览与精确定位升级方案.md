# DAY9 补充：来源原文件预览与精确定位升级方案

状态：阶段 A 与阶段 C 已完成；DOCX 技术路线已验证，XLSX 轻量 Viewer 已停止。完整
Word Viewer、Excel 高保真方案和跨格式真实 Run 回归尚未实施。

## 1. 结论

本次升级可行，但要先统一“原始预览”的定义：来源抽屉必须读取当前 Run 固定快照中的
**完整原始文件**，不能继续只展示检索 Chunk；浏览器渲染效果应尽量接近原应用，但不承诺
与 Microsoft Word、Microsoft Excel 或装有任意插件/主题的 Obsidian 像素级一致。

推荐方案如下：

| 格式 | 推荐预览方案 | 定位与黄色高亮 | 结论 |
| --- | --- | --- | --- |
| PDF | 保留当前原文件 + `#page=N` 方案 | 继续按物理页定位，暂不改动 | 已有能力 |
| TXT | 读取完整原始文本，按行渲染 | `startLine-endLine` 定位并高亮 | 可完整实现 |
| Markdown | 读取完整 `.md`，复用 Streamdown，并补 Obsidian 语法、附件解析与安全 HTML 规则 | 行号 + 文本引用双定位，滚动后黄色高亮 | 可实现约定范围内的 Obsidian 风格 |
| DOCX | `docx-preview` 在浏览器直接读取原始 DOCX 字节并渲染 | 文本引用定位；图片来源补稳定图片锚点 | 可实现高保真预览，不是 Word 像素级还原 |
| XLSX | 先验证 `@extend-ai/react-xlsx`，通过后直接读取原始 XLSX 字节 | 切换工作表、滚动到 Range、黄色覆盖层 | 能力匹配，但必须先过技术验证 |

该范围不是一个小样式补丁。它会同时影响来源契约、解析定位、附件授权、客户端渲染和
多格式验收，预计需要 **4～6 个工作日**；若强行插在 D10 前，原四周计划应同步顺延或
削减后续范围。

## 2. 对三个疑问的直接回答

### 2.1 Markdown 能否做到“Obsidian 里什么样，预览就什么样” 

能做到项目约定范围内高度一致，不能对任意 Obsidian 环境做无条件的一比一承诺。

本次 P0 应明确支持：

- 标题、段落、列表、任务列表、引用、表格、删除线、代码块和普通 Markdown 图片。
- `![[图片.png]]`、`![[目录/图片.png|宽度]]` 等 Obsidian 本地图片嵌入。
- `==高亮==`。
- 截图中的 `<mark style="background:lightgreen;">done</mark>`，保留为浅绿色高亮。
- 当前项目已经安装的代码高亮、CJK、数学公式和 Mermaid 能力。
- 点击来源后打开完整 Markdown，自动滚动到命中块，并用黄色临时覆盖命中位置。

不能承诺自动复刻：

- 用户自己的 Obsidian 主题、CSS Snippets、社区插件、Dataview/Templater 查询结果。
- 插件生成的动态图表、脚本、iframe 和任意可执行 HTML。
- 未随 Vault 一起导入的本地图片或附件。

原因是 Obsidian 的最终显示不仅由 Markdown 文件决定，还由主题、插件、设置和附件目录
共同决定。VaultAgent 应复刻受控的 Obsidian Flavored Markdown，而不是嵌入或重做整个
Obsidian。

安全规则：允许 `mark` 等明确标签，但不直接放行任意内联 HTML/CSS。`mark` 的背景色只
接受颜色白名单并转换为受控样式；`script`、事件属性、危险 URL、iframe 等继续由
Streamdown 的 sanitize/harden 链路拒绝。来源黄色定位高亮显示期间优先于文档原有绿色
高亮，关闭来源或切换引用后恢复原样。

### 2.2 Word 能否原文件预览并定位

可以做到“由原始 DOCX 字节驱动的高保真只读预览”。`docx-preview` 会把 DOCX 渲染为
HTML，可展示常规分页、标题、段落、表格、页眉页脚、脚注和图片。但其官方说明也明确：
渲染受 HTML 能力限制，实时重新分页没有完整实现，所以不能写成与桌面 Word 像素级一致。

当前 `blockIndex` 只能说明解析顺序，不足以在渲染后的 DOM 中稳定找到重复文本。本次需
在 DOCX 解析时额外保存短文本引用：`exact + prefix + suffix + occurrence`。预览完成后
跨 DOM Text Node 建立 Range，滚动并包裹黄色 `<mark>`；定位失败时明确显示“已打开原文，
但未能自动定位”，并保留当前解析片段作为辅助，不得伪造成功。

DOCX 内嵌图片来源不能只依赖 `imageIndex`。技术验证需确认渲染顺序与 OOXML 关系能否稳定
映射；不稳定时应把关系 ID/媒体路径或内容哈希补入定位器，再高亮对应图片容器。

### 2.3 Excel 能否原文件预览并定位

可以，但这是三种格式中风险最高的一项。现有 ExcelJS 适合解析，不是完整的 Excel
查看器；自己用表格组件拼装会丢失大量格式、图表、冻结窗格和图片能力，不建议继续造
一套简化 Excel。

推荐先验证 `@extend-ai/react-xlsx`。它能直接读取 `ArrayBuffer`，支持工作表、合并单元格、
格式、冻结窗格、图片、图表、只读模式和渲染态单元格样式，正好可以用当前
`sheetName + range` 定位器给目标区域加黄色背景而不修改工作簿数据。

但该库发布时间较新，必须先用真实文件验证以下硬门槛：

1. 能在 Next.js 16 + React 19 + Turbopack/生产构建中加载本地 WASM。
2. 能按 `sheetName` 切换工作表，并把 `A12:D18` 自动滚动到可视区域。
3. 黄色高亮是纯展示层，不写回原 XLSX，也不覆盖文件自身格式数据。
4. 中文工作表名、合并单元格、隐藏行列、公式缓存值、图片和常见图表显示可接受。
5. 关闭抽屉后能释放 Worker、对象 URL 和工作簿内存。

任一门槛失败，不直接接入生产链路。备选是自托管 ONLYOFFICE Document Server；它的
Office 保真度更高，但会新增 Docker 服务、JWT/短时文件 URL、服务间网络、插件开发和
AGPL/商业授权评估，不适合作为 DAY9 的无成本小升级。

## 3. 当前实现差距

现有 DAY9 来源抽屉有以下明确缺口：

- `SourcePreview.documentUrl` 只对 PDF 返回，MD/TXT/DOCX/XLSX 仍只有 Chunk 文本。
- 抽屉把内容统一标成“解析片段”，没有格式级 Viewer 分派。
- Markdown 虽然记录 `attachments`，但没有把 Vault 相对路径解析为同一快照内的受权附件。
- Markdown/TXT 已有行号，DOCX 已有块序号，XLSX 已有 Sheet/Range，但缺少统一的
  “打开完整文件 → 定位 → 高亮 → 失败降级”结果状态。
- DOCX Chunk 正文可能带人为追加的标题上下文，不能直接拿整个 Chunk 去全文匹配。
- 抽屉当前最大宽度约 36rem，不适合完整 Word 页或 Excel 网格。

## 4. 目标交互

点击回答中的来源后：

1. 打开右侧宽抽屉；桌面端建议 `min(76vw, 1120px)`，移动端占满屏幕。
2. 先显示文件名、格式和引用位置，再请求来源元数据及原文件。
3. 根据 MIME 动态加载对应 Viewer，避免 Word/Excel 依赖进入首屏聊天包。
4. Viewer 完成渲染后定位来源；成功则滚动到目标并显示黄色高亮。
5. 高亮只表达“本次回答引用的位置”，不能修改原文件，也不能与原文自带的高亮混为一谈。
6. 失败时区分“文件读取失败”“格式渲染失败”“原文已打开但定位失败”，保留重试。
7. 抽屉底部可折叠显示当前解析 Chunk，作为定位失败时的辅助证据，不再作为主预览。

## 5. 来源定位契约升级

不新建一套脱离现有 `SourceLocator` 的万能框架，而是在已被多格式共同验证的定位契约中
补充必要字段：

```ts
type TextQuoteSelector = {
  exact: string;
  prefix?: string;
  suffix?: string;
  occurrence?: number;
};

type SourceHighlight =
  | { kind: "line-range"; startLine: number; endLine: number; quote?: TextQuoteSelector }
  | { kind: "docx-text"; blockIndex: number; quote: TextQuoteSelector }
  | { kind: "docx-image"; relationshipId?: string; contentHash?: string }
  | { kind: "xlsx-range"; sheetName: string; range: string }
  | { kind: "pdf-page"; pageNumber: number };
```

约束：

- `SourceLocator` 仍负责文件内稳定位置；`SourceHighlight` 只负责 Viewer 定位表现。
- `exact` 必须来自原始块，不包含为检索追加的“标题路径”等合成内容。
- 长 Chunk 保存实际分片对应的短引用，不重复存整段原文。
- `prefix/suffix/occurrence` 用于解决文档中重复句子的歧义。
- 新字段继续存入现有 JSON 定位列，无需数据库列迁移；已有旧索引不伪造精确定位。
- 本地开发阶段对旧 DOCX/MD 重新索引即可获得新定位；旧记录只使用现有块/行降级。

## 6. 服务端与附件授权

### 6.1 原文件读取

- 现有 `/api/runs/[runId]/sources/[chunkId]/file` 扩展为所有受支持格式共用。
- 继续从 `Run → Snapshot → Chunk → FileVersion` 重建授权，不返回 Blob URL、存储键或本地路径。
- 保留 `private, no-store`；文件大小继续遵守现有导入上限。
- 来源元数据返回 `viewerKind`、`fileUrl`、`sourceLocator` 和 `sourceHighlight`，不在 JSON 中塞入
  完整二进制或整个私有文档正文。

### 6.2 Markdown 本地图片

新增受鉴权的 Markdown 附件读取入口，按当前 Markdown 文件所在目录和 Run 快照解析目标：

1. 规范化分隔符并拒绝绝对路径、`..` 越界、重复解码和未知协议。
2. 优先匹配相对当前笔记目录的路径。
3. 再匹配 Vault 根路径。
4. 仅在文件名全 Vault 唯一时允许 Obsidian 式短链接匹配；重名时明确报歧义，不猜测。
5. 目标文件必须属于同一 Run 固定快照，且 MIME 在允许的图片类型中。
6. 只返回受鉴权响应 URL，不暴露附件的真实存储位置。

普通 `![](path/image.png)` 和 `![[path/image.png|宽度]]` 都在渲染前转换为该受权 URL。
远程图片默认不自动加载，避免浏览器向第三方泄露访问时间、IP 和来源页；后续如确实需要，
再设计显式加载或服务端代理策略。

## 7. 前端文件结构建议

生产代码继续使用长期领域职责命名，不出现 DAY9：

```text
components/sources/
├─ source-drawer.tsx              抽屉外壳、加载/失败/定位状态
├─ source-document-viewer.tsx     按 MIME 分派 Viewer
├─ markdown-source-viewer.tsx     Obsidian 风格 Markdown 与附件
├─ text-source-viewer.tsx         TXT 完整原文与行定位
├─ docx-source-viewer.tsx         DOCX 动态加载、DOM Range 定位
└─ xlsx-source-viewer.tsx         XLSX 动态加载、Sheet/Range 定位

lib/sources/
├─ reader.ts                      Run 快照授权与原文件读取
├─ attachment-resolver.ts         Markdown 附件路径解析和授权
├─ source-highlight.ts            文本引用匹配与定位结果
└─ types.ts                       预览与定位契约
```

Viewer 自身保留独立异步状态，`source-drawer.tsx` 只负责组合，避免把四种格式的加载、渲染、
滚动和清理继续堆在一个组件中。

## 9. 实施顺序

### 阶段 A：定位与依赖技术验证

- 用真实 DOCX 验证 `docx-preview@0.4.0` 的页、表格、图片和跨节点文本高亮。
- 用真实 XLSX 验证 `@extend-ai/react-xlsx` 的构建、WASM、Sheet 切换、Range 滚动和黄色覆盖层。
- 技术验证失败就停止对应方案并记录原因，不先改主链路。

#### 阶段 A 实际记录（2026-09-14）

验证环境：Node 22、Next.js 16.3.4、React 19.2.8、Turbopack；所有浏览器检查只读取
仓库内 `fixtures/office/` 的脱敏 fixture，不读取用户资料、不接入 Run 授权或生产来源抽屉。

| 项目 | 实际结果 | 决策 |
| --- | --- | --- |
| `docx-preview@0.4.0` | 通过生产构建；`vaultagent-docx-multipage-test.docx` 在浏览器中渲染出多页、表格与内嵌图片。以“模块 06 导入验证”为短文本引用，跨 DOM Text Node 成功滚动并精确黄色高亮。`Range.surroundContents()` 不适用于跨部分内联节点，正式实现应采用安全的片段包裹逻辑。 | 保留依赖，可进入后续 DOCX Viewer 实现。 |
| `@extend-ai/react-xlsx@0.16.4` | 本站静态 WASM、Worker、Next.js 生产构建、`Overview` 工作表切换与 `A1:D1` 选择均可运行；但真实 `vaultagent-xlsx-fixture.xlsx` 的网格未渲染已有文字、数值和公式缓存值，仅能看到网格与图片。现有公开 Controller 也没有可供来源抽屉调用的 Range 自动滚动 API。 | 不通过，已移除依赖与临时 WASM；不进入来源主链路。 |

补充验证：现有 `exceljs@4.4.0` 能读取上述 XLSX 的 `A1:D1`（项目、数量、单价、总计）、
`A2:D4` 数值与公式缓存值，故 XLSX Viewer 空白并非 fixture 没有单元格内容。

阶段 A 结论：DOCX 技术路线可行；XLSX 轻量 Viewer 方案停止，不能在后续阶段宣称 Excel
原文件高保真预览或自动定位。若产品仍要求该能力，应重新评审 ONLYOFFICE Document Server
或另一个已通过真实 fixture 的 Viewer，且必须单独确认新增部署与授权成本。

#### Excel 备选方案复核记录（2026-09-14）

| 候选 | 实际验证 | 结论 |
| --- | --- | --- |
| `jspreadsheet-ce@5.0.4` | 临时只读页面通过现有 `exceljs` 读取 `vaultagent-xlsx-fixture.xlsx`，可显示 `Overview` 的单元格、公式缓存值，并对 `A1:D4` 叠加定位样式；生产构建、类型检查和定向 ESLint 均通过。该包本身没有读取 XLSX 原文件的能力，必须先由服务端转换数据；fixture 内嵌图片也未在网格中渲染。临时页面和依赖均已删除。 | 不通过。只能作为数据网格，不能满足原文件预览、样式/图片保真和来源定位目标。 |

当前决定：Excel 继续维持既有 `ExcelJS` 解析、检索与 `sheetName + range` 引用，不接入原文件
预览或自动定位。个人开源项目不等于自动取得 Syncfusion 授权；即使符合 Community License，
也仍需按其规则完成注册和资格确认。若后续必须做高保真 Excel 预览，应另开技术决策，明确
选择自托管 Syncfusion .NET 服务或 ONLYOFFICE Document Server，并确认部署、数据流和许可证。

#### 阶段 C 实际记录（2026-09-14）

- 来源接口为 Markdown/TXT 返回受鉴权的 `fileUrl` 与 `line-range` 定位信息；来源抽屉改为
  展示完整原文，原有解析片段收进“当前解析片段”折叠区。
- TXT 按原始行序显示，自动滚动到 `startLine`，并只对 `startLine` 到 `endLine` 使用语义黄色
  引用高亮。Markdown 使用 Streamdown 的现有 CJK、代码、数学和 Mermaid 插件渲染，`==...==`

## 10. 验收清单

### Markdown/TXT

- 截图中的 `<mark style="background:lightgreen;">done</mark>` 在非引用状态显示浅绿色。
- 点击该处来源后滚动到命中位置，并由黄色引用高亮临时覆盖。
- 普通 Markdown 图片和 `![[...]]` 图片均从同一快照的受权附件显示。
- 中文/空格路径可用；缺失、重名和越界路径给出不同错误。
- 标题、列表、表格、代码、公式、Mermaid 以及长文档滚动不回退成纯文本。

### DOCX

- 直接使用受权 API 返回的原 DOCX 字节，不使用 Mammoth 的 Chunk HTML 充当原文件预览。
- 常规分页、标题、段落、列表、表格、页眉页脚和内嵌图片可见。
- 重复句子、跨多个文本节点的句子仍定位到正确一次并黄色高亮。
- 图片引用能滚动到对应图片；不能稳定定位时明确失败，不高亮错误图片。

### XLSX

- 原始工作簿的所有工作表可切换，常见样式、合并单元格、公式显示值和图片可见。
- 点击来源会切换到正确工作表，滚动到准确 Range，并只在渲染层显示黄色。
- 视觉来源按已有 `sheetName + anchor` 定位图片附近。
- 工作簿始终只读，引用高亮不会写入下载文件或数据库。

### 安全与资源

- 所有原文件和附件仍通过 Run/快照/文件版本授权；构造其他 Chunk ID 或附件路径返回 404/403。
- 响应为 `private, no-store`，不暴露 Blob URL、存储键和本地路径。
- 任意 Markdown HTML 不能执行脚本、事件处理器或危险 URL。
- 切换引用、关闭抽屉和请求取消后清理旧正文、Worker、对象 URL 和高亮 DOM。

## 11. 方案决策门

建议先批准“阶段 A 技术验证 + 阶段 C Markdown/TXT”，再决定是否把 Word/Excel 全部插入
D10 之前。原因不是依赖能不能安装，而是 Excel 自动定位和 Word 图片锚点必须用真实文件
证明稳定；未验证就直接扩大来源主链路，会让已经完成的 DAY9 重新变成不可验收状态。

若产品要求是“与桌面 Word/Excel 像素级一致”，应停止轻量方案并单独评审 ONLYOFFICE；
若接受“由原始文件驱动、主要格式与版式高保真、引用位置可靠”，则按本方案实施。
