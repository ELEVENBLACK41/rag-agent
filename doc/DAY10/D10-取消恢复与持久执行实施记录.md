# DAY10 第三阶段：取消、恢复与验证

状态：用户已验收第二阶段并完成 CR；第三阶段按授权实现，等待用户验收。

## 实现与边界

- `POST /api/chat` 创建领域 Run、固定当前快照并派发现有 Workflow，返回 Run ID。浏览器不再驱动模型执行。Workflow 只持久传递 Run ID，问题、历史和证据仍从领域数据库读取。
- Workflow 的模型执行步骤先写入 `execution_started` 认领记录。步骤重派时，已经开始且未完成的尝试明确失败；已提交终态的尝试直接结束。不自动重放模型生成，也不承诺模型调用恰好一次。
- Workflow 使用持久定时器约束执行期限；领域 Run 的总期限为创建后 120 秒，包含排队时间。事件和历史读取也会对超期 Run 收敛失败，覆盖创建后派发前进程退出的间隙。该间隙没有 Workflow 的记录，需后续读取触发收敛，未增加全局扫描器。
- 服务端取消写入 `cancelled` 和 `run_cancelled`。执行器每 500ms 检查持久状态，并在每次工具启动前检查；Agent、最终回答、查询向量和重排序使用取消信号。已发出的数据库只读查询不保证撤销，后续事件和终态写回受到数据库门禁保护。
- 所有 Run 写入统一按“会话 → Run”顺序加数据库行锁。事件序号在同一锁内分配，完成消息、完成事件和终态在同一事务提交；取消、失败、删除与完成竞争只接受首个有效终态。同一会话只允许一个运行中的回答，避免并行问答缺少彼此上下文。
- 模型正文逐增量保存；事务提交后通过 PostgreSQL NOTIFY 唤醒 SSE 订阅，移除 300ms 固定合并窗口。公开事件保存后才可被客户端读取。实时和历史使用同一事件转换，按 `sequence` 去重，来源与正文继续分开。旧事件格式仅保留历史读取兼容。
- 浏览器创建 Run 后只建立一条持续 SSE 连接，使用 `after` 游标先补齐历史，再由数据库通知驱动后续推送，终态关闭连接。仅在异常断线时退避重连同一个 Run，连续 6 次无进展失败后提示重新加载；刷新、切换再打开会话自动接续运行中尝试，不重新提交问题。服务端每 15 秒进行空闲保活和权限/期限检查，正文不等待心跳。
- 用户主动重试创建新 Run，重新选择当前快照，并在事务内将旧尝试标记为已替换。历史默认只显示新尝试，原失败/取消记录保留；旧执行无法覆盖新答案。重试归属、原问题、旧终态与重复替换都由服务端校验。
- 直接回答和结构化最终回答达到长度上限时明确失败，不把截断内容保存为完整答案。SDK 原始错误不直接返回客户端；领域错误提供可展示的原因。

## 实际验证

| 验证 | 结果 |
| --- | --- |
| 数据库并发事务 | 20 个并发事件写入序号连续且唯一；完成/取消/失败竞争只有一个终态，助手消息与完成事件数量一致 |
| 取消与删除门禁 | 取消后迟到正文、完成和失败不能改写终态；删除后事件、历史和取消入口不可访问，迟到完成被拒绝 |
| 重试与事件去重 | 原问题创建新尝试；重复重试被拒绝；历史只显示替换后的问答；同一批事件应用两次，正文和过程不重复 |
| 断线与编码探针 | 模拟一次网络失败后使用原游标恢复；重复事件不重复正文；中文/emoji 按字节切分及 CRLF 帧解析通过 |
| 检索取消探针 | 已取消信号传入检索后明确中止，不被向量/重排降级逻辑吞掉 |
| 工作区隔离 | 其他工作区 Run 的事件读取、取消与完成写入均被拒绝 |
| 中断与超期探针 | 已认领执行再次进入时失败且保留部分正文；超期未派发 Run 收敛为失败 |
| 真实模型与浏览器 | 问候失败后点击重试，Qwen 返回“你好！”；刷新后只显示新尝试、无重复问题或来源按钮 |
| 真实取消 | 工具执行中点击停止，数据库记录 `cancelled`；浏览器显示已停止并提供重试，原尝试没有完成事件或助手最终消息 |
| 生成中刷新 | 长篇虚构故事生成中刷新，历史恢复已保存正文并继续接收同一 Run 的后续增量 |
| 真实进程重启 | 在部分正文持久化后停止本轮独立测试端口的服务；重启日志确认 Postgres World 重新派发 1 个活动任务。原 Run 仅 1 条认领、1 条失败事件，保留 25 条公开事件，没有第二次模型生成或完成写入；浏览器显示中断失败与重试入口 |
| 静态检查 | Next.js 路由类型生成、定向 ESLint、TypeScript、最终生产构建及 `git diff --check` 均通过 |

并发探针仅创建自己的临时会话和工作区，结束后按记录 ID 清理，并确认没有残留；浏览器只使用本轮临时会话，不删除用户会话或知识库。Python 环境没有 Playwright，浏览器实际验证使用内置浏览器控制工具，没有安装测试依赖。

## 限制与验收建议

- 这是“持久派发、终态收敛和安全重试”，不宣称能从模型生成到一半的 Token 原地续写，也未持久化 Agent 每一个工具的内部状态。重派已认领步骤时，选择明确失败是本阶段的有意边界。
- 本地构建和真实模型已验证；没有部署或验证 Vercel 托管环境。沙箱首次类型检查/构建无法读取既有 `class-variance-authority`，首次模型请求被沙箱 `EACCES` 阻止；沙箱外验证正常，没有重装依赖。
- 真实断网切换未单独操作系统网络开关；已验证生成中刷新、订阅重建和服务重启，不能据此声称所有网络代理异常都已覆盖。
- 之前已验收的资料比较、证据不足和各格式来源定位未全量重测。一次一般知识长问题仍触发模型搜索，随后用于主动取消验证；此次没有借机调整已验收提示词，也不声称模型检索选择永远正确。
- 数据库仍存在第二阶段已记录的 `runs.snapshot_id` 非空约束，仓库 `0007_allow_snapshotless_chat.sql` 尚未应用到当前数据库。本阶段没有修改迁移记录；当前有已发布快照的真实问答通过，无已发布快照的数据库创建路径仍受该迁移状态限制。
- Workflow 官方的 `Promise.race + sleep` 超时模式在本地 SDK 可能记录剩余 sleep 的提示；领域成功/取消状态已独立提交，不将该提示当作模型失败。依据：[Workflow 超时模式](https://useworkflow.dev/docs/foundations/common-patterns)、[AI SDK 取消信号](https://ai-sdk.dev/docs/reference/ai-sdk-core/tool-loop-agent)。

建议人工验收：发送问题 → 生成中刷新 → 主动停止 → 重试并替换 → 切换会话再返回。确认停止文案、部分回答标记、重试替换与来源展示符合预期。

## 持续 SSE 修正（2026-09-16）

用户指出请求列表不断出现 `events?after=...`，且正文呈轮询感。上一版有限 SSE 批次方案确实属于客户端轮询，本次予以替换，不能将前次通过的功能验证视为流式交互已达标。

- 正常请求数为一次创建请求和一条持续 events 连接；原有会话列表刷新请求独立保留。
- 同一事务写入事件并 `pg_notify`，通知仅包含 Run ID；先 LISTEN 再回放，避免监听建立期间的事件遗漏。Postgres.js 共用专用监听连接，断线重连时再次补齐；客户端离开后解除对应监听。
- 不新增依赖或队列。LISTEN 需要支持会话级监听的数据库连接，不能使用不支持 LISTEN 的事务连接池；本次验证使用现有本地 PostgreSQL，未验证托管连接配置。
- 实际数据库探针通过：同一连接在 EOF 前收到两段独立正文、完成后关闭、从中间游标只补缺失事件、断开订阅后后台仍可写入。临时数据和探针已清理。

- 本次最终验证：定向 ESLint、TypeScript、生产构建通过。真实 HTTP + Qwen 调用只发起 1 次 events 请求，同一连接收到 22 个正文增量；首段约 2284ms、整轮约 3633ms，终态为 `run_completed`。这是单次观测，不作为性能保证。测试会话通过产品删除接口清理，临时脚本删除，独立测试服务停止。
