# DAY10：查询路由与引用门禁规划

状态：已完成方案选型，尚未实施代码与验收。2026-09-14 已确认本地多步骤 Agent 为 D10 硬性范围，不再作为可选恢复项。本规划补齐“普通对话也检索并显示来源”的已知问题，并把本地工具循环作为 D10 冻结聊天/RAG 范围前的发布门槛。

## 放在 D10 的原因

- D8 已提供混合检索与 rerank，D9 已提供答案流式生成和来源抽屉；问题出在两者之间缺少“本轮是否需要知识库”的决策，以及生成后缺少“实际引用了哪些候选”的发布门禁。
- D10 本来就负责多轮追问、SSE 恢复和聊天/RAG 冻结。查询路由需要有限会话历史，引用门禁又会改变完成事件和历史消息，因此在 D10 一次收口比回填 D8/D9 或另设阶段更合适。
- AI Elements 继续负责聊天界面、生成状态和来源展示；是否检索、哪些引用可以发布属于服务端业务规则，不能靠隐藏前端按钮修复。

## 最小方案

请求流程：

> 当前消息 + 受限历史 → 结构化 `QueryPlan` → `direct` 直接生成，或 `retrieve` 执行现有混合检索 → 流式答案 → 提取答案中的引用编号 → 服务端校验 → 只发布实际使用的来源。

`QueryPlan` 首版只包含两个必要字段：

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `route` | `direct` / `retrieve` / `agent` | `direct` 不检索；`retrieve` 复用现有单次 RAG；`agent` 执行 D10 必须交付的本地多步骤工具循环。 |
| `searchQuery` | `string \| null` | 知识问题或省略主语的追问使用改写结果；直接回答时为 `null`。 |

路由使用项目现有的 Vercel AI SDK 7 与 Zod：`generateText({ output: Output.object({ schema }) })`。这与当前视觉分析的结构化输出方式一致，不新增依赖、不自行解析模型 JSON，也不增加 LangChain、LangGraph 或专用意图分类框架。

官方资料：

- [AI SDK：Generating Structured Data](https://ai-sdk.dev/docs/ai-sdk-core/generating-structured-data)
- [AI SDK：Output API](https://ai-sdk.dev/docs/reference/ai-sdk-core/output)
- [AI SDK：Agent Loop Control](https://ai-sdk.dev/docs/agents/loop-control)

## 路由规则

| 场景 | 路由 | 行为 |
| --- | --- | --- |
| 问候、致谢、能力/身份说明 | `direct` | 不执行检索，正常流式回答，完成事件中的引用为 `[]`。 |
| 信息不足，需要先询问用户 | `direct` | 直接提出一个澄清问题，不拿无关文档填充上下文。 |
| 询问已导入资料、文件内容或基于资料总结比较 | `retrieve` | 使用改写后的问题走现有关键词、向量、RRF 和 rerank。 |
| 省略主语的追问，如“那第二页呢” | `retrieve` | 结合有限历史补齐检索问题，保留原始用户消息用于回答。 |
| 需要多次搜索、读取或关联扩展 | `agent` | D10 必须启用；由路由选择后再进入工具循环，不能对全部消息强制首步 `search_notes`。 |

不维护不断膨胀的问候关键词正则。少量完全确定、无模型价值的系统命令可以继续使用程序分支，但自然语言意图由结构化路由统一处理。

## 引用发布门禁

- `retrievalCandidates`：检索和 rerank 得到、发送给模型的内部候选，可以包含最终未使用的资料。
- `answerCitations`：最终答案正文中出现的 `【n】` 对应来源。服务器确认编号属于当前 Run、固定快照和 `retrievalCandidates` 后才写入助手消息并通过完成事件发送给前端。
- `direct` 路径固定发布空数组。前端只渲染服务端发布的 `answerCitations`，不自行从候选推断来源。
- 候选不足时，模型明确说明当前 Vault 中没有足够依据，可以不引用任何来源；“检索返回了内容”不等于“这些内容支持答案”。
- 模型生成不存在的编号时按生成错误处理并记录 Trace，不创建伪来源。首版不增加第二次模型验证调用；先用编号白名单和服务端归属校验解决真实性问题。
- 暂不写死 rerank 分数阈值。不同模型的分数未必可直接比较，先用无答案样本观察分布，再决定是否增加经评测校准的证据阈值。

## 预计代码落点

| 位置 | 责任 |
| --- | --- |
| `lib/chat/query-router.ts` | 新增稳定的 `QueryPlan` Schema、路由提示词和结构化生成；失败时保守降级到 `retrieve` 并留下 Trace。 |
| `lib/chat/runs.ts` | 在检索前调用路由；实现 `direct`/`retrieve` 分支；生成结束后提取、校验并发布 `answerCitations`。 |
| `lib/agent/run-agent.ts` | 接收已判定的 `agent` 路由和服务端已完成的初始检索候选；使用 AI SDK `ToolLoopAgent`、`prepareStep` 和有界 `stopWhen` 执行本地工具循环，删除对所有消息无条件强制 `search_notes` 的行为。 |
| `lib/agent/tools.ts` | 保留检索与来源读取；将“已读正文再次检索”的 `find_related` 重构为同文受限上下文扩展和 Markdown 内部链接跟随，避免工具循环退化为多绕一层 RAG。 |
| 聊天接口与消息类型 | 明确区分候选和已发布引用；SSE `complete` 事件只携带 `answerCitations`。 |
| `components/chat/agent-process.tsx` | 使用 AI Elements `ChainOfThought` 组合阶段性回答和工具事件；运行中展开，完成后折叠，不读取私密 reasoning。 |
| `components/chat/**` | 使用 `Conversation` 承载消息滚动，使用折叠区外的 `MessageResponse` 展示唯一最终回答；继续消费完成事件并展示引用，不复制服务端路由或引用判断。 |

不为两个字段引入全局状态库；路由结果属于一次 Run 的服务端状态。只有后续多个独立客户端区域确实需要共享复杂状态时，才重新评估 Zustand。

## 实施顺序

1. 增加 `QueryPlan` Schema 和结构化路由，保存路由类型、改写问题、耗时、模型和用量 Trace。
2. 为 `direct` 增加不检索的流式回答分支，并确保完成事件与持久化消息的引用均为空。
3. 把现有 `sources` 语义拆成内部候选与发布引用；从最终答案提取 `【n】`，完成服务器白名单和 Run/快照归属校验。
4. 接入有限会话历史，验证省略主语的追问会改写为可检索问题。
5. `agent` 路由先复用服务端初始检索并将候选目录写入 Run State，不让模型为相同检索额外调用工具；再将当前 `find_related` 重构为同文受限上下文扩展与 Markdown 内部链接跟随。用复合问题验收一次来源读取、一次真实关系扩展，以及充分/不足两种退出；仅证据缺口场景验收二次定向 `search_notes`；D10 验收不通过时不得冻结聊天/RAG 范围。
6. 用回归样本决定是否需要证据分数阈值；没有数据前不扩大实现。

## 验收门槛

| 用例 | 预期结果 |
| --- | --- |
| “你好” | `direct`；检索与 rerank 未执行；回答无来源按钮。 |
| “你是谁/你能做什么” | `direct`；回答产品能力边界；引用为 `[]`。 |
| “这份 PDF 讲了什么” | `retrieve`；只展示答案正文实际使用且可打开的页码来源。 |
| 检索得到 8 个候选、答案只使用 2 个 | 持久化和界面仅有 2 个引用，其余候选只留在受限 Trace。 |
| “那第二页呢” | 使用有限历史生成完整 `searchQuery`，仍能定位当前资料和页码。 |
| Vault 中不存在答案 | 明确说明证据不足，不拿最相似但无关的片段充当来源。 |
| 一个问题需要检索并读取多个来源 | 路由为 `agent`；服务端先执行一次初始检索，Agent 至少真实执行一次来源读取，以及同文上下文扩展或 Markdown 链接跟随；工具结果进入 State，最终回答只引用实际使用的来源。 |
| 读完初始来源仍有证据缺口 | Agent 才调用一次二次定向 `search_notes`；若仍不足，输出部分完成，不将二次检索变成无界循环。 |
| 本地多步检索后仍证据不足 | Agent 输出部分完成结果和缺失证据；D10 不伪装完成，D12 再接入获准后的联网搜索。 |
| 阶段性回答后继续调用工具 | 阶段文字先在执行过程区流式出现，随后才显示对应工具事件；刷新恢复后顺序不变，最终回答仍独立位于折叠区外。 |
| 路由结构化输出失败 | Run 不伪装成功；保守降级到 `retrieve`，Trace 可看到失败与降级。 |
| 模型输出不存在的 `【n】` | 不创建可点击伪来源，按生成错误记录和处理。 |

发布前至少执行类型检查、聊天/RAG 定向检查、上述回归样本和 `git diff --check`。未完成真实回归前，不把本规划标记为已实现。

## 非目标

- 不展示模型完整私密思维链；只显示可审计的路由结果、工具动作和证据。
- 不安装新的 Agent、路由、工作流或向量数据库框架。
- 不用前端条件隐藏掩盖服务端仍然错误发布引用的问题。
- 不在首版增加第二个“引用验证模型”调用，也不让所有消息进入多步 Agent；但被路由为 `agent` 的复合知识任务必须执行真实工具循环。

## 截图交互目标

- 红框是同一个 Run 的可折叠执行过程，不是单纯的 Loading，也不是模型私密思维链。它按服务器事件顺序保存和渲染阶段性回答、工具开始、工具结果、错误与下一步动作。
- 阶段性回答可以先于后续工具调用真实出现，例如“本地资料显示两个版本不一致，接下来核对官方资料”，随后再显示联网搜索工具；不能在 Run 完成后一次性补写成假过程。
- 红框运行中默认展开并持续更新，完成后自动折叠为“用时/状态”标题，用户可重新展开。每个工具活动默认紧凑，必要时可二次展开脱敏参数和结果。
- 蓝框是折叠区外唯一的最终回答或部分完成报告，只在 Agent 完成目标判断后开始流式发布；引用按钮跟随蓝框，不把所有检索候选直接显示为来源。
- 使用 AI Elements `ChainOfThought`、`MessageResponse`、`Tool` 和 `ChainOfThoughtStep` 组合红框，使用 `MessageResponse` 渲染蓝框。组件名称虽然是 Chain of Thought，但这里只承载公开、可审计的 Run 过程事件，不传入模型私密 reasoning。
- 使用 AI Elements `Conversation`、`ConversationContent` 和 `ConversationScrollButton` 承载整个聊天区域：位于底部时跟随流式内容；用户向上查看历史后停止自动抢滚，并显示回到底部按钮。

官方组件依据：[Chain of Thought](https://elements.ai-sdk.dev/components/chain-of-thought)、[Tool](https://elements.ai-sdk.dev/components/tool)、[Conversation](https://elements.ai-sdk.dev/components/conversation)。实施时只按需安装缺少的 `chain-of-thought` 和 `tool`，不安装完整 AI Elements 组件集。
